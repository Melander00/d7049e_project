## Workshop 3 — Entity System Design draft

### 1. Runtime object model decision

We use a **component-based runtime model with lightweight entity IDs and data-owning component stores**.

This fits our engine because our main gameplay objects share many runtime features but combine them in different ways. The player, enemies, projectiles, and barrels can all have `Transform`, `Render`, `Physics`, and `Collider`, but only some need `Agent`, `Script`, `Camera`, or `Pickup`. This lets us build around reusable systems instead of a deep object hierarchy.

**Accepted drawback:** Behavior is spread across several systems, so debugging and ownership are less obvious than in a single large object class.

**Rejected alternative:** A monolithic class hierarchy is awkward for our shooter objects, which overlap heavily but do not fit cleanly into inheritance.

---

### 2. Trade-offs

| Aspect | Benefit | Cost / Risk |
|---|---|---|
| Composition over inheritance | Objects like player and enemy share components without forcing a hierarchy | Behavior spread across systems; harder to trace a single object's logic |
| ID-based references | No dangling pointer bugs when entities are destroyed | Requires ID validity checks; slightly more indirection |
| Data-owning stores | Cache-friendly iteration over component arrays | Shared state (e.g. Transform) needs clear ownership rules |
| ScriptSystem as extension point | Game logic stays out of engine code | Script/engine boundary must be kept clean; errors harder to trace |
| Camera on player entity (MVP) | Simple, no extra entity needed | Assumes single follow camera; needs revisiting if scope grows |

---

### 3. How we use entities, components, and systems

- **Entities** are runtime IDs representing active gameplay objects.
- **Components** store the state needed by systems.
- **Systems** implement engine logic and update matching entities.

The **engine layer** provides systems for movement, physics, collision, rendering, camera, profiling, and scripting. The **game layer** defines which entities exist and which components they carry.

---

### 4. Ownership rules

- An entity is an **ID**, not a rich object.
- Each component type lives in its own component store.
- Systems access entities through component queries, not object pointers.
- External references use **entity IDs**, not raw pointers.
- When an entity is destroyed, its components are removed from their stores and the ID becomes invalid.

**Shared state:** `TransformComponent` is the shared runtime state for position, rotation, and scale. `MovementSystem`, `PhysicsSystem`, `CameraSystem`, and `RenderSystem` all read from it. `PhysicsComponent` holds the Bullet-side rigid body handle; `TransformComponent` holds the engine-side spatial state.

---

### 5. Core components

| Component | Key fields |
|---|---|
| `TransformComponent` | position, rotation, scale |
| `RenderComponent` | model ID, material/texture ID, visible flag |
| `PhysicsComponent` | Bullet rigid body handle, mass, gravity flag, dynamic/static flag |
| `VelocityComponent` | linear velocity, movement speed |
| `ColliderComponent` | collision shape, layer/mask, trigger flag |
| `HealthComponent` | current HP, max HP |
| `AgentComponent` | behavior type, current state, target entity ID |
| `ScriptComponent` | script ID/reference, exposed parameters/bindings |
| `CameraComponent` | follow offset, smoothing value |
| `ProjectileComponent` | damage, owner entity ID, speed |
| `LifetimeComponent` | remaining lifetime |
| `GateComponent` | open/closed state |
| `PickupComponent` | pickup type, value/effect ID |

---

### 6. Real object breakdown

| Object | Entity? | Components | Shared data / state | Messages |
|---|---|---|---|---|
| Player | Yes | Transform, Render, Physics, Velocity, Collider, Camera, Health | position, sideways speed, HP | `MoveIntent`, `CollisionEntered`, `DamageTaken` |
| Enemy | Yes | Transform, Render, Physics, Velocity, Collider, Health, Script, Agent | position, velocity, HP, AI state | `CollisionEntered`, `DamageTaken`, `Died` |
| Projectile | Yes | Transform, Render, Physics, Velocity, Collider, Projectile, Lifetime | position, velocity, damage, owner ID, TTL | `CollisionEntered`, `DestroyRequested` |
| Barrel | Yes | Transform, Render, Physics, Collider, Health, Script | position, HP, reward type | `CollisionEntered`, `DamageTaken`, `Destroyed` |
| Gate | Yes | Transform, Render, Collider, Gate | position, open/closed state | `OpenGate`, `CloseGate` |
| Item / Pickup | Yes | Transform, Render, Collider, Pickup | pickup type, effect value | `Collected`, `DestroyRequested` |
| Ground | No | static level geometry + static collision setup | static collision and render data | none |
| Camera | No | `CameraComponent` on player entity (MVP) | follow offset, smoothing | none |

Ground is not a gameplay entity in the MVP — it is scene data with static collision. Camera is not a separate entity — one follow camera on the player is sufficient for current scope.

---

### 7. Core systems

| System | Responsibility |
|---|---|
| `InputSystem` | Reads player input each frame; writes movement, shoot, pause, and quit intent |
| `MovementSystem` | Processes movement intent; updates velocity for fixed-step simulation |
| `AgentSystem` | Runs enemy decision logic; updates AI state |
| `PhysicsSystem` | Steps Bullet physics; syncs engine transform state with physics results |
| `CollisionSystem` | Reads collision results; emits gameplay messages |
| `CameraSystem` | Updates follow camera from player transform and physics state |
| `ScriptSystem` | Runs script-driven entity behavior — primary extension point for game logic |
| `AnimationSystem` | Updates visual animation state |
| `RenderSystem` | Draws models, world geometry, and UI |
| `ProfilingSystem` | Collects frame timings, FPS, and debug data |

---

### 8. Message flow

| Message | Sent by | Used for |
|---|---|---|
| `CollisionEntered(entityA, entityB)` | `CollisionSystem` | Projectile hits, item pickup, gate contact, trigger reactions |
| `DamageTaken(target, amount, source)` | Collision / combat logic | Reducing HP; triggering scripted or audio reactions |
| `DestroyRequested(entity)` | Projectile, pickup, barrel, or lifetime logic | Safe removal after the current update |

Messages keep systems decoupled and let scripted behavior react to engine events without direct system dependencies.

---

### 9. Minimal API outline

```java
Entity createEntity();
void destroyEntity(Entity e);

<T> void addComponent(Entity e, T component);
<T> void removeComponent(Entity e);
<T> boolean hasComponent(Entity e);
<T> T getComponent(Entity e);

void sendMessage(Message m);
void update(float dt);

// Prints entity ID and all currently attached components with their field values.
// Used during development to verify component setup and catch missing components.
void debugInspect(Entity e);
```
